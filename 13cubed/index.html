Watching the USN Journal Work on a Live System

We usually treat the USN Journal as a dead artifact. We pull it out of an image, we parse it, and we read about things that already happened. But you can also query the journal on a live and running system — no extraction, no parsing — and watch it record file system activity as you cause it: a create, a rename, a delete, each one sitting right there in the journal moments after you do it.

Now remember, NTFS gives us two file system journals: $LogFile and $UsnJrnl — or more accurately $J, since $J is an alternate data stream of $UsnJrnl. $J is what we would typically extract with a tool like FTK Imager or KAPE, and then parse with a tool like Eric Zimmerman's MFTECmd. That's the workflow most people know, and I've covered both journals in depth before, including how to extract and parse them. This is a different look: querying the journal directly on the live system.

Create a file, then predict the journal

Open an administrative command prompt. To create a file, I like to use copy con — con as in console — an old-school method that dates back to the MS-DOS days but still works fine in modern Windows:

`` copy con testfile ``

Press Enter and you get a blank line. Type something like "hello world", then press F6 (or Ctrl+Z) and Enter, and Windows reports that one file was copied. A quick dir testfile confirms it's there.

Before touching the journal, think about what we'd expect it to contain for this file. We created a file, so there should be a file create. We added data to it, so that gets logged as a data extend. And then we closed the handle. That's our prediction — now let's test it.

The commonly documented method, and why it falls short

Here's one method I often see documented for querying the USN Journal on a live system:

`` fsutil usn readdata testfile ``

This does produce information — but notice the timestamp. It's listed as 12:00 AM on 1/1/1601. That's the NTFS epoch, the beginning of time from the perspective of Windows NTFS. Clearly not the actual time anything happened to this file.

We do get a file reference number, or FRN. Remember that the FRN is an 8-byte value: a combination of the MFT entry number, which is 6 bytes, and the MFT sequence number, which is 2 bytes. We also get the parent FRN and the update sequence number. But the reason field just reads 0x0. There's no file create in sight. This doesn't seem to be what we're looking for, and that's because it's not. We need different parameters.

readjournal is what you actually want

`` fsutil usn readjournal c: csv ``

That's the drive letter the journal lives on, and csv tells fsutil we want CSV output. One warning: run it exactly like that and it dumps the entire journal to standard output. That's a huge amount of data flying past, and none of it is helpful at that speed. Ctrl+C to abort, then run it again with a filter. We're not in WSL, so there's no grep here — use findstr instead:

`` fsutil usn readjournal c: csv | findstr /i testfile ``

The /i makes the match case-insensitive. I do that out of habit.

Now we get something back that looks like what we predicted: a file create, then a data extend alongside the file create, and finally data extend, file create, and close together. Exactly the three operations we expected — and this time with a timestamp that looks reasonable.

One thing to keep in mind about that timestamp: it's displayed in whatever time zone the local machine is configured for, even though behind the scenes the journal stores it in UTC. So don't let the local time display throw you.

Following the file through a rename and a delete

Before moving on, copy the FRN out of that output — we're about to need it.

Now let's generate some more noise in the journal. Rename testfile to testfile2, then delete testfile2. Here's the catch when we go looking for that activity: the file carried two different names over its life, and testfile2 was only the last of them. So instead of searching the journal for a filename, search it for the FRN. That should show us everything.

Reading the results top to bottom: our file create; the data extend with file create; the data extend, file create, and close. All of that is the history we already saw. But then comes a rename old name entry for testfile, a rename new name entry for testfile2, a rename new name with close — and finally a file delete with close, where we deleted the newly renamed testfile2.

That's the entire life of the file, from creation to deletion, exactly as we just lived it on the file system — and you can see it live, on a running machine, with nothing but fsutil.

Pretty cool, right? It's one thing to hear about how something should work. But it's an entirely different thing when you get to actually see it live and in action.
